## 0. 为什么先做这一轮

这一轮要测掉的是当时排名最高的几个未知：**共享 CA 并发首启的竞态**、
**hosts 语义导致的 502**、**改写造成的上游连接复用丧失**、**孤儿进程**。
它们的共同点是：**都不需要规则移植或工作台就绪就能验证**，而一旦不成立，
上连改写机制与共享 CA 的选型都要改。所以先花一轮把它们测掉。

## 1. 共享 CA 并发首启

**问题**：`certs.py` 的 CA 是懒生成且**无锁**的（`certs.py:524-529`，已核读）；
N 个实例共享 confdir 并发首启时，会不会各写一份、互相覆盖，导致客户端随机证书错误？

做法分两步，因为这里有两件不同的事：

1. **契约路径**（1a–1c）：**先把 CA 物化出来，再并发拉起 4 个实例** —— 这是产品契约要求的
   顺序（**管理器必须在拉起任何实例之前**物化 CA），然后逐个取回每个实例对客户端
   出示的叶子证书，用**磁盘上的那一张 CA** 去校验；
2. **原始竞态**（1e）：在**全新 confdir** 上并发首启，重复 5 轮，既看磁盘上的
   key/cert 配对，也数一数"有几个实例在用一张已被覆盖的 CA 签叶子"。

| 断言 | 结果 | 证据 |
|---|---|---|
| 1a 预物化 CA 后四个实例都起来，confdir 里 CA 齐备 | PASS | `up=[27100,27101,27102,27103]`，文件 `mitmproxy-ca-cert.pem` / `mitmproxy-ca.pem` / `mitmproxy-dhparam.pem` |
| 1b CA 私钥与证书配对 | PASS | `key_pub_sha=e38684626075` == `cert_pub_sha=e38684626075` |
| 1c **四个实例都在用同一张 CA** | PASS | 4 个叶子证书逐一 `openssl verify -CAfile <磁盘 CA>` → 全部 `OK` |
| 1d 负例：把证书改坏后校验失败 | PASS | `no certificate found` —— 证明 1c 的断言有区分力，不是"总能过" |
| 1e 空 confdir 并发首启 5 轮 × 4 实例：磁盘配对 | PASS | `broken=0/5`（最后一轮写入者留下的是**成对**的 key/cert） |
| 1e（同批，仅记录）实例实际在用的 CA | — | 20 张叶子里 **3 张**对不上磁盘 CA |

**怎么读这个结果**：机制成立 —— 只要 CA 在磁盘上配对，所有实例就真的在同一张 CA 下工作。
但 1e 那 3/20 才是关键：**空 confdir 并发首启真的会让个别实例用一张已被覆盖的 CA 签叶子**，
客户端于是随机报证书错误；而磁盘上的 key/cert 是配对的，所以"只看磁盘文件"永远发现不了。
这正是「先物化 CA、再拉起实例」这条约定的实测依据（此前只能说「0/5 不等于不会有」，
现在有正例）：

- 预物化的顺序**必须**是"先物化、再拉起实例"，而不是"起来之后再检查"；
- 就绪判据**必须**校验私钥与证书配对（1d 证明"文件齐全"不足以判定 CA 可用）。

> 记账方式：1c 判的是**契约路径**（确定性），1e 的叶子数只是**观测**（不稳定，取决于
> 覆盖的交错），所以它不作 PASS/FAIL —— 早先把这四个实例直接当成原始竞态去断言
> "四张叶子都能验证"，会让 `live` 层随机变红（实测约一半的运行会红）。

## 2. HTTPS 改写：SNI / Host / 上游校验

**问题**：`server_connect` 改写上连地址之后，上游看到的 SNI 还是原域名吗？
上游证书不匹配时的行为是否符合文档？逃生门（`ssl_insecure=true`）有效吗？

做法：本地起一个 HTTPS 服务（自签证书 `CN=spike.test`，并用 `sni_callback` 记录
客户端发来的 SNI），规则把 `spike.test` 改写为 `127.0.0.1`，客户端用 curl 经代理访问。

| 断言 | 结果 | 证据 |
|---|---|---|
| 2a 默认 `ssl_insecure=false` + 上游自签 → 502 | PASS | `http_code=502` |
| 2b `ssl_insecure=true` → 200 且**改写确实生效** | PASS | `http_code=200`，本地服务收到 `/relaxed` 请求 |
| 2c **上游收到的 SNI 仍是原域名** | PASS | 服务端 `sni_callback` 记录 `sni='spike.test'`（不是 `127.0.0.1`） |
| 2d Host 头未被改写 | PASS | 服务端记录 `host_header='spike.test:27099'` |
| 2e 对照组：不在规则里的域名不被改写 | PASS | 该域名 `rewrite=None`，请求不成功 |

**两个必须写进文档的细节**：

1. **2c 是整套方案的立足点**：改写只动"往哪连"，客户端看到的一切（SNI、Host）不变。
   这正是 hosts 覆盖该有的语义，也解释了为什么不用 `mapremote`（它通过改
   `flow.request.url` 连带改掉 Host，属于过度动作）。
2. **2e 的观测方式容易误读**：mitmproxy 对 CONNECT 回的是 `502`
   （curl 原文：`CONNECT tunnel failed, response 502`），但 curl 的 `%{http_code}`
   是 **000** —— 隧道没建成，根本没有"目标请求的响应码"。排查时如果只盯
   `%{http_code}`，会把"上游解析失败"误判成"连接被重置"。文档要按这个区分写。

**仍然未验证的一项**（诚实记账）：改写路径上的 `sni is None` 分支（此时
`addons/tlsconfig.py:291` 会回退用**已改写**的地址当校验主机名）。curl 走显式代理时
总会带 SNI，构造不出这个分支；它目前仍只是**源码核读结论**，不是实测结论。
触发它的现实场景是透明模式或连接复用路径 —— M2 的实例化测试里如果再构造不出，
应在文档里保持"源码核读、未实测"的标注，不要写成已实测。

## 3. 上游连接复用

**问题**：改写是否真的让被覆盖的 host 失去上游连接复用？（一开始的估计是
「影响很小」；按源码核读改为「完全不复用」，这里给出实测。）

做法：客户端用一条 curl 命令连打 4 个同 host 的请求（复用客户端连接），
注入器在 `server_connect` 里计数。

| 断言 | 结果 | 证据 |
|---|---|---|
| 3a 未被改写：4 个请求复用 1 条上游连接 | PASS | `localhost server_connect=1` |
| 3b 被改写：4 个请求各建一条上游连接 | PASS | `reuse.test server_connect=4` |

**结论**：代价是真的，且量级是「每个请求一次新上连 + 一次 TLS 握手」。
它写进 README 的「已知限制」，并作为「要不要为热点域名提供直连旁路」的决策依据 ——
这是设计选择，不是实现缺陷。

## 4. 孤儿进程清理

**问题**：管理器崩溃/被杀后，实例进程会不会变成孤儿一直占着端口？

做法：父进程用 `preexec_fn` + `prctl(PR_SET_PDEATHSIG, SIGTERM)` 拉起 `sleep 30`
后立即退出，检查子进程是否随之结束。

| 断言 | 结果 | 证据 |
|---|---|---|
| 4a 父进程退出后子进程结束 | PASS | `child pid=89522 alive_after_parent_exit=False` |

**结论**：Linux 上 `PR_SET_PDEATHSIG` 可用（此前只有"头文件存在"的间接证据，
现在是进程内实测）。macOS/Windows 没有这个机制，由注入器轮询 `getppid()`
兜底 —— 那条路径**未实测**（本机没有那两个平台）。

## 5. Windows 侧端口可达性 —— 未验证

本机 `/etc/wsl.conf` 里 `[interop] enabled = false`，`netsh.exe` / `cmd.exe` /
`curl.exe` 全部无法执行（`UtilAcceptVsock: accept4 failed 110`），注册表 hive 也无读权限。
因此：

* **Windows/Hyper-V 保留端口段与 16000–16999 是否相交：无法确认**；
* **Windows → Linux 方向的连通性：无法直接实测**（只能证明反方向：Linux 能连上
  Windows 独有的 135/445/5040/7680，且这些在 `ss -ltn` 里看不见 —— 说明 mirrored
  模式下 loopback 共享，但不等于反向一定通）。

**这条记为「已知的未知」**，缓解手段是「分配成功 ≠ 客户端可用」：
实例起来后要有一次真实连通性验证 + 启动失败换端口重试。等真在 Windows 侧验收
工作台时（M3 的浏览器验收会用到），再补一次实测。

## 6. 本轮测掉之后定下的约定

| 发现 | 据此定下的约定（本仓生效） |
|---|---|
| CA 就绪判据不能只看文件齐全（1d） | 就绪判据是「文件存在 + 可加载 + 私钥/证书配对」，不配对就幂等重建 |
| 改写后 SNI/Host 不变（2c/2d） | 上连改写只动「往哪连」；`sni is None` 分支保持「源码核读、未实测」标注（见第 2 节） |
| CONNECT 上游失败时 curl 看到 000 而非 502（2e） | 本文档记录；写文档时按「隧道失败」与「目标响应码」区分 |
| 连接复用确实丧失，量级为每请求一次握手（3b） | 按此措辞写进 README 的「已知限制」（不是「影响很小」） |
| `PR_SET_PDEATHSIG` 实测可用（4a） | 实例拉起时设置该标志；非 Linux 平台由注入器轮询 `getppid()` 兜底（未实测） |
| Windows 侧端口可达性仍未知（5） | 保持「已知的未知」，缓解手段不变 |
